# ADR 0254 — the word a function returns is read from what its body does

Date: 2026-10-02 · Status: Accepted · Roadmap: L11.6 (numeric truth in the compiled backend), Gap R.3c (closed), Gap R.102 / R.103 / R.104 (filed), ADR 0196 (parameters are locals), ADR 0253 (the double domain), ADR 0174 (strings and floats across a function boundary), ADR 0166 (a broken module is our bug), ADR 0186 (the oracle), ADR 0138

## Context

ADR 0253 fixed a module and, in doing so, exposed a wrong answer underneath it. `programs/probe_float_param_rebind` had been **exit 2** since ADR 0196 — `llc` rejecting `%p0` defined with type `double` but expected `i32` — and once the store-happens-once rule of ADR 0253 made that module verify, the leg started printing:

```
def addf(x):
    x = x + 1.5
    return x

print(addf(1.0))    # CPython 2.5 · --interp 2.5 · --aot printed 1, exit 0
```

A number-shaped answer that is simply the wrong one, with the exit code of success. That is ADR 0166's worst class, and it had been sitting behind an `llc` rejection for two hundred ADRs.

The cause was that a function's calling convention was **written twice, from two unrelated questions**. The argument words come from the call sites (ADR 0174 infers them from annotations, defaults and the arguments actually passed). The return word comes from `funcReturnsFloat`, which asks `g.isFloat` of each `return` **expression**. `return x + 0.0` is visibly a double, so that function is emitted `double`. `return x` is a name, and a name says nothing to a syntactic question: the function was emitted `i32`, the body's `%_x = alloca double` had already happened, and the answer came back truncated — the callee reading its own parameter's incoming register instead of the double the body stored.

The same weakness had already filed one symptom as a worse bug. `return -x` of such a parameter reached **no gate at all**: `isFloat` answers a unary minus by asking its operand, and at the moment the return word is chosen the parameter is not yet known to be a float, because `floatVars` is filled while the body is generated — *after* the header is written. The module was emitted `define double` with `ret i32` of a `fsub double 0.0` at the end, and `llc` rejected it. A pre-existing row (`TestReturningAReboundParameterNegatedIsFiledNotFixed`) had pinned that rejection as "worse than a refusal, but not this ADR's".

What made the two questions one again was not a new analysis. It was noticing that the backend **already has** the right predicate — `isFloat` is what the arithmetic, the negation, the float-box and `print` all consult — and that it was being asked the return question with a table it had not been given yet.

## Decision

**The return word is asked of the predicate the emitted body will itself use.** `funcDef` calls `floatReboundReturnAsksForTheDouble` before writing the header: it copies the float-variable table, adds the names the body rebinds to a float, and asks `funcReturnsFloat` — the same function, the same `isFloat`, the same statement walk — against the copy. Promote iff it says yes. The `ret` and the value it writes are then answers to one question, which is exactly what the module verifier checks and exactly what `return -x` had been getting wrong.

**What is at stake is a statement-shape question, not a "does the body mention a float" question.** `returnedFloatRebindings` (in `params.go`, beside the ADR 0196 copy-in analysis it extends) intersects two scans: names the body binds to a float value, and names some `return` reads back — a bare name, an arithmetic expression over it, its negation, a kind-preserving numeric builtin of it (`abs`, `float`, `min`, `max`), or a ternary arm holding it. Both the parameter spelling and the local spelling are in scope (`y = x + 0.5; return y` is the same lie, and answers `0`), and the walk goes through `if`/`elif`/`else`, `while`/`for` (+ `else`), `with`, `try`/`except`/`finally` and `match`. Restricting the set this way is what keeps the gate from over-reaching: `return int(x)`, `return round(x)`, `return x > 2` and `return str(x)` are not at stake, so they are not promoted (which would put an `i32` in a double's word) and not refused (which would take away answers that are correct today).

**A refusal is emitted only where the word cannot carry the answer, and it is emitted before the header.** Two shapes reach it, both measured rather than theorised — forcing the promotion through them produces the module `llc` rejects, so the gate asks instead:

- a **mixed signature**, where the parameter convention that decides the answer's word also decides every parameter's word, so a container parameter (whose word is a heap handle) or an interned-text parameter (whose word is an index into `@str_tab`) cannot be handed a `double` — `def f(xs, y): y = y + 0.5; print(xs[0]); return y` came out `sitofp i32 @.lst1 to double` and `print(s)` came out `call void @rt_print_str(i32 %p1)` with `%p1` a `double`;
- a **method**, which is emitted `i32`-returning whatever its body computes: the receiver's word and the answer's word are fixed together there, so a method with this body is refused rather than emitted to answer the argument.

Both refusals name the variable whose double has nowhere to go, say what to write instead, and are exit 1 through the codegen-refusal class — never exit 2, never `LLVM ERROR`, never the verifier's prose.

**The ternary is refused too, and that is a new honest edge, not a regression.** `return x if x > 2 else 0.0` of such a parameter answered `1` with exit 0: `isFloat` has no `CondExpr` arm, so the promotion does not run, and the i32 word truncated the arm. There is no number-typed `select` in this backend to choose two doubles with, so the answer is refused with its own message. Filed as **Gap R.102**.

## Consequences

- Gap R.3c closes. `programs/probe_float_param_rebind.gy` was promoted out of the oracle ledger into `conformanceStandalone()`, prints `2.5 / 3.0 / -2.5 -3.5 -1.5 / 2.5` on all three legs, and is `match` in the matrix — the third probe promoted this session for answering rather than for being re-pinned.
- What answers now, both engines, checked against `python3`: the bare name, an int or bool argument into a promoted body, `return x * 2`, `x + 0`, `x % 3`, `x // 1`, `return -x` (three call sites, one of them negative-in-negative-out), `return abs(x)`, `return abs(-x)`, `return float(x)`, `y = x + 0.5; return y`, a return inside `if`/`while`/`try`, a recursive promoted function, a promoted function with a default, a promoted function beside a nested `def`, and the answer used inside a larger expression.
- What is untouched, and pinned so: `return int(x)` and `return round(x)` still answer `2`, `return x > 2` still answers with the bool word, a parameter rebound to an int or to text keeps its own word, and a user callee's return word stays that callee's question.
- Pinned by `pkg/lang/float_rebound_return_test.go` (29 parity rows × both engines, 7 refusals each required to name its missing half and forbidden from reaching the toolchain, an IR row that requires `define double` for a promoted body and `define i32` for the same source with no rebind, and an IR row for the negation: `fsub double 0.0` in the body, `ret double` at the end, no `ret i32 %` in a promoted function) and `integration/float_rebound_return_test.go` (the same 23 + 7 through the shipped CLI against CPython, with exit 2 failing the file, plus the corpus program's three-leg row). The row that had pinned the negation's `llc` rejection was replaced by a parity row on the day the emission learned — as that row instructed.
- Three shapes measured on the way and **filed rather than absorbed**: **Gap R.102**, the ternary arm above (the fix is a number-typed `select`, which the ternary lowering has never had); **Gap R.103**, `def f(x): return {"k": x}` with a computed float prints `0` on the compiled leg where the interpreter and CPython print `{'k': 2.5}` — **[corrected 2026-10-02, next cycle]** the control without the function, `x = 2.5` / `print({"k": x})`, prints `{'k': 2.5}` on all three engines, so the missing word is the *returned container's kind* (**Gap R.67**), not a dict-literal tag; the row stays, wording corrected, because a row filed from one program's symptom before the control was run is exactly what the record should not hide; and **Gap R.104**, `min(x, 1.0)` / `max(x, 1.0)` with two arguments refusing in the **interpreter** (`min/max expects 1 argument`) while the compiled leg and CPython answer — the one defect of this family that lives on the interactive path.
- Agentic path: no new flag, no new exit class, no schema change. The two refusal sentences are stable strings added to the capability-message table in `docs/operations.md`, so a script matches them the way it matches the rest, and `--json --aot` reports them as `{"error": …, "backend": "aot", "exit": 1}`. What changed for a script is that the twenty-three programs of the parity table now exit 0, and the seven that cannot carry the answer say so in one sentence each, naming the variable, instead of failing in `llc`.

## Alternatives rejected

- **Promote whenever the body stores a float into a parameter.** The first cut of this change. It is a "does the body mention a float" question, so it also promoted `return int(x)` and `return x > 2`, which answer with an `i32` — the same `ret i32` under a `define double` this ADR exists to eliminate, arriving by a different road. The at-stake set has to be a statement shape, and the promote/refuse decision has to be the predicate's own answer.
- **Permanently mark a float-rebound parameter in `floatVars` before the body runs.** One table, no copy — and then `def f(x): x = x + 1.5; x = 3; return x` reads the second binding through the first variable's word, because a name can only have one entry in that table. The overlay is scoped to the question, which is the only reason it is safe to ask it early (ADR 0196's copy-in is where a parameter's *slot* is decided, and that stays there).
- **Promote mixed signatures too, converting the container argument.** It is one line at the call site and it is `sitofp i32 @.lst1 to double`: the callee would read a list's static global as a number. The word a container crosses a boundary in is a heap handle (ADR 0174, `docs/language.md` § Containers across function boundaries), and a signature that mixes handles, interned indices and doubles is the tagged value word's, not a patch to this gate.
- **Refuse the whole family until L11.6 lands the tagged value word.** Honest, and the reason it is wrong is measured: the twenty-three rows of the parity table answer with the promotion — programs a script had to route around — while the seven that cannot carry the answer refuse themselves with a message that names the variable. Refusing the answers to avoid the refusals would trade twenty-three correct programs for nothing.
- **Teach methods the double return in this change.** It looks like the same patch and is not: a method's parameters and its receiver are emitted by `emitClassMethod` under one convention, and every call site of a method reads the answer through the `i32` word the dispatch was written for. Doing it properly is the tagged value word arriving at dispatch (L11.1 (5) × L11.6), which is a feature in its own right; here a method is refused in words and the interpreter answers it.
- **Leave the negation pinned as an `llc` rejection.** The row said "the row fails the day the emission learns", and the emission learned for the cheapest reason available — the body already emitted `fsub double 0.0`; only the header had been guessed. A toolchain rejection of a program the language allows is a bug we own (ADR 0166), not a state to keep pinning.
